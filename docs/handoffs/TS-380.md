基线为线上 R7 `d9c1452c01f30350b2861afd3458e157a6a863af`；分支 `codex/chain-platform-20261028`。产品源提交按顺序为 `54aa1ccbbfb245c3c630c26f5ca9313f1470897e`、`b314458ef338b5b4569eafc1485b9745ff454e17`，后者是最终产品源码 SHA。本地隔离实现、验证和提交；集成、Linux/真实 PostgreSQL、192.168.31.230 发布与实测由协调者负责。

## 503 证据与修复

协调者在 R7 原生 TLS 入口做五轮只读双请求，五轮均是一条 200/九项 `ok`，另一条在 3.417–8.885ms 内返回 503/九项 `not_verified`；实际成功检查为 108.585–756.289ms。安全原始记录位于协调仓库 `.runtime/chain-optimization-20261028/ready-overlap-r7-r1.json`。这证明本次波动来自 `Probe.ready` 的 `_inflight` 立即拒绝分支，无需猜测 PostgreSQL 故障。

- `runtime_health.Probe` 保持单个真实检查，保存其 Future 与最初的事件循环截止时间；重叠读者只等待该轮剩余预算，共享真实成功或失败。
- 原 2 秒预算、1 秒 TTL、九项闭集、默认 executor 和缓存开始时间语义保持。读者取消不取消检查、不释放实际所有权、不影响其他读者；超预算仍是 `not_verified`，不延长预算、不复用过期绿灯。
- 提交 executor 失败时恢复所有权，避免永久 `_inflight`；结果落地仍经 `_settle` 处理真实完成。
- 每个已登记 PostgreSQL schema 仍通过 shared 0.1.3 的原 `handle.connect(read_only=True, timeout=.25)` 进行安装/逻辑库绑定核验。产品自身元数据版本行、历史表清单及实际表从三条校验 SQL 合为一条只读 SELECT；17 个 schema 的校验 SQL 为 51→17，连接绑定检查没有略过。
- 启动时的 `WebAccount` 对象供探针复用，账户内容/封印仍每轮真实读取，不缓存权限或账户结论。

公开网页 app 在 `server.py` 的既有边界中先拒绝 `/health/live` 和 `/health/ready`，返回 404。它创建的闲置 Probe 不会执行第二轮 schema 检查。因此没有新增 Platform 共享 Probe、跨 app Future 或生命周期层，也没有修改公开探针边界；`server.py` 最终未变。真实新增回归覆盖公开拒绝且不触发 pass、关闭公开 app 不影响原生探针，以及原显式 `probe=` 注入。

## 链路与实际重复点

| 链路 | 实现归属、实际重复及处理 |
| --- | --- |
| 原生健康/交互 | `server.py → runtime_health.py → backends.py/postgres.py`。修复并发观察者假 503，减少完整 schema 检查往返。TS-379 的 LocalWork 总 4 worker/16 准入、媒体后台 3 配额保持；未把 Probe 挪入媒体池。 |
| 音乐网页 | `media/web.py → music/web.py → MusicLibrary/Catalog/Maintenance`。会话、Origin/CSRF、回执和账号修订继续由原入口负责；详情/导出原来逐曲重复查 track/source/alias/file/settings/job，改为原事务内批读与请求阶段复用。 |
| 搜索与渠道 | `Resolver.matching_tracks/offers → Netease/Bridge → MetadataCache/RequestControl`。来源批读；元数据原来一个锁包住所有 query 的远端 await，现按完整缓存键分锁，引用归零移除；同键复用、刷新/账号修订失效、取消清理均保留。原供应商/账号节流、额度、冷却、实际下载授权与取消结算未放松。 |
| 订阅同步/排队 | `music/runtime.scan → library.complete_scan/install_snapshot → queue.enqueue_playlist`。快照刚注册来源后原来立即再注册一次；同事务传递已登记 binding，所有注册完成后解析最终别名、批取已有最早可见任务。track/request/job 查找批量化，继续保留共享录音任务、顺序/重复成员、请求版本及幂等回执。 |
| 下载/选路/归档 | `Downloads.run → Resolver.requests/offers → Selection → AudioStorage.finish_job`。需求聚合原来每 request/playlist 新开连接和事务，现一个原事务批读后合并；严格最低音质、worker 完成前 request_version 复核、全部账号候选比较、回执及所有权不变。 |
| 原件/索引 | `Imports.ensure_indexed/scan/index/mark_missing`。未变文件原来逐文件读取 observation、再逐文件新开库解析 catalog/file；现批读本轮观察与别名。文件 stat、摘要、实际音频核验均在事务外；标记缺失时复核 artifact revision 和当前 canonical id，避免旧读取覆盖期间的新发布。进度/失败路径两个同步 `self.view()` 读取也移回原 LocalWork。 |
| 归档后导出 | `AudioStorage.export_related → MusicLibrary.export_snapshot → Navidrome mark_dirty`。原 request/playlist/source 多次开库，改为一轮原事务批读；关联判定和实际文件输出继续分开，原库目录锁、fsync 和内容核验保留。 |
| 维护/后台 | `Background.run → Maintenance.pump/plan`。原 plan 对每个已完成任务重复查 request、两次 alias、file/check，并在列表中查成员；现先批读，成员用 set，沿原单个事务只选择一个到期录音。周维护暂停、前台优先、冷却补齐、lease/generation、取消、后台公平都保留。 |

公共读取只加到原 `Repository._documents/_jobs`，单批最多 256 个标识；payload 仍走原恢复读取。音乐 `CatalogReads` 只存在于一个事务的读取阶段，复用原 alias 解析和质量规范化规则，身份/文件变化后不跨阶段沿用。没有新增数据库、表、依赖、缓存权限、配置开关或迁移。
