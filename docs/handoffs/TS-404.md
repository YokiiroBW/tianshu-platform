## 确认问题与修改

1. `web_life_management._call` 原仅 image.request 网络错误带 unknown，普通 activity/日程订阅等写超时会成为普通 dependency_unavailable；Companion 的真实 `409 result_unknown + execution_state=unknown` 还会被转成 invalid_upstream。现接受该 owner code，绑定原 request_id 后保留 unknown/not_started；原可写端口网络失败标 unknown，无自动重试、无新键。正常读取网络失败仍为普通不可用。现有 integrationPost/writeFailure 可消费该字段，同语义 client_id 由原界面保留。
2. `WebPeopleLife.route` 先等待 proactive/control，再执行订阅写；原权限/target 复核只有请求开始与写后。当 control 等待期间 session 或 target scope 撤销，写可能先发生。抽取原复核到 `_recheck` 并用于写前与返回前；不加新权限或确认门禁，不借控制台身份扩 scope。
3. `sessionTransport.webFetch` 原克隆并解析所有成功 JSON，调用者随后再次解析，聊天轮询/记忆列表/内容读取因此重复 buffer/parse。仅错误响应与 `/api/web/session` 需要检查会话状态，普通成功响应现直接交调用者；未做无依据性能数字宣称。

## 退役与风险边界

本轮未发现已无调用且无兼容价值的可删业务路径：group policy v1 normalization 仍承担既有配置兼容；HTTPS fallback 仍服务非单容器部署；旧 adapter/投递路径仍有真实调用，不能因原生 SDK 存在就删除。仅合并此次重复的 PeopleLife 原复核逻辑，无平行规则系统。

写请求发出后再撤销、网络中断后的最终 owner 状态不能由浏览器取消证明回滚；仍使用 owner 幂等/状态恢复，不把 unknown 当未执行。新复核修复控制读期间已可观察到的撤销，不声称跨 owner 原子授权事务。网络错误发生在发送前也可能保守呈现 unknown；平台无法证明对方未处理，不自动重发。

未访问生产、真实聊天/账号/凭据，未发 QQ、模型调用或推送部署；不新增外接功能。后续集成及受影响实机验收由协调者串行执行。
