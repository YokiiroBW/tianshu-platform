# TS-172 音乐渠道独立补查与 Navidrome 精确文件匹配

基线：`a932c50f7a2e1d6034499df273cc99719c41852e`。本任务继续用户已授权的音乐功能修复、推送、部署与实机验证；不清理其他任务或既有音乐原件。

## 变更

- 查询、资料补全、音频探测或下载遇到某个渠道的预算/冷却等待时，记录渠道、原因和恢复时间，并继续比较其他可查询渠道。全部渠道暂不可用且没有合格本地文件时才等待，不消耗歌曲重试次数。
- 有可用结果时比较实际音质并归档，报告明确标记“部分渠道待补查”，不宣称受限渠道已完成比较。原文件与待补查记录在同一 SQLite 事务中保存；恢复后沿用同一歌曲任务补查。补查可与新歌队列一起推进，每次维护调度最多加入一个；正常每周巡检仍在新下载之后。
- 复用原音质比较、完整音频校验、共享录音/成品索引、归档替换和 Navidrome 同步。相同或更好的本地音频不再完整下载，只替换实际音质更高的成品，不为补查另建下载任务。
- Navidrome 的 Subsonic 展示路径会将不同文件名映射成相同路径；仅对歧义候选读取同账号原生 API 的真实文件路径，核对歌曲 ID、音乐库、大小和路径后选定已有归档。短时缓存查询结果与会话；失败时保留歧义，其他歌曲仍可同步。不读写 Navidrome 数据库实现产品功能，不删除旧文件或重建歌单。
- 页面区分已检查账号和待补查渠道，展示当前选择和后续补查语义。

- 前端类型检查、构建、格式以及音乐页桌面/手机共 22 项浏览器检查通过，包括待补查信息。
- 已只读核验正式 Navidrome 0.64.2 的 12 个候选：6 对歌曲分别是原文件及带时间戳的旧文件名；原生接口可返回真实路径。正式歌单修改、恢复队列和发布后验证待执行，不能据此称已修好线上。
- 安装后的 Linux 候选、发布冷备/恢复验证、服务健康与正式音乐复测待完成后更新本交接。

原生接口按已部署版本核对：[Navidrome 0.64.2 路由](https://github.com/navidrome/navidrome/blob/v0.64.2/server/nativeapi/native_api.go)、[音频文件模型](https://github.com/navidrome/navidrome/blob/v0.64.2/model/mediafile.go)、[认证实现](https://github.com/navidrome/navidrome/blob/v0.64.2/server/auth.go)。它用于消除路径歧义，歌单管理继续使用 Subsonic。

渠道额度不调整、不重置，12 小时歌单同步及每周巡检设置保持。暂不可查询的渠道不能证明其最高音质；因此保存当前可用最高音质并保留后续升级检查。真实歌曲的权限或失效源仍可能无法下载。
