## 维护期新增第24个逻辑源

新入口只可用于**已有active PG**：

```text
python -I -m services.platform.plugins.bootstrap --settings /etc/tianshu/settings.json
```

它先只读确认现有PG绑定，再复用`backends.start → Repository → backends.database(runtime,"plugins",<database_path>.plugins.sqlite) → StorageRuntime.database/prepare`登记原生新源，随后复用`Vault`与`Packages`初始化本地密钥与包缓存，最后关闭runtime。没有Platform组合根、业务loop、插件工作进程、Owner锁或调度器；只有共享连接池生命周期。异常不输出设置或密钥。

维护runtime只登记新源时**不调用finalize**：原16逻辑源仍在`_expected`但未在该runtime装配，finalize会正确拒绝。`database()`本身已在原生事务中创建/校验schema、标ready并原子追加active binding，close不丢弃登记。正式Platform随后正常装配原16和plugins并finalize17。没有手写binding/SQL、重跑原库迁移或重置原PG。

默认namespace=tianshu时，新schema为`ts_tianshu_platform_plugins_ec1a83c47791`；Platform16→17，全局23→24。原绑定中的installation_id、namespace、epoch和原16的逻辑名/schema必须保持；其他服务7源保持。已有同名但不归本installation所有的schema仍拒绝。若锚点旧plugins SQLite存在，原prepare只读导入并核对；本批线上尚无插件，应为空新源。

`test_plugins_pg.PluginPostgresTests.test_active_binding_adds_plugins_and_legacy_registration_preserves_state`在独立namespace建立16个已有源及每源marker，维护入口追加plugins，重新登记原16+启动新宿主后finalize，再证明旧子集finalize拒绝、薄登记兼容回退可finalize且16个marker及插件KV仍在。此用例本机只做加载/静态，未连PG；真实全局23→24还须协调者对实际五服务绑定清单和前/后冷备自证，不能把合成16→17用例冒称线上证明。

维护初始化可能已提交schema/binding后才遇到key/cache权限错误，应保留现场、修正路径后重试；不能删binding、旧库或重建密钥冒称回滚。
