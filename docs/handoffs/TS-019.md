### P2：授权库列表丢掉分页信息，第一页之后的库进不去

**复现**：先跑协调自己的探针（`.runtime/probe019.spec.ts` + `probe019.config.ts`），返修前
`LIBRARY_PAGE_HAS_MORE=true ROWS=1 CONTINUE_BUTTONS=0`，`expect(继续按钮).toBeVisible()` 失败；
返修后同一条探针 `LIBRARY_PAGE_HAS_MORE=true ROWS=1 CONTINUE_BUTTONS=1`，**1 passed**。

**根因**（两处，缺一不可）：`useAssetPage` 只保存了 `listed.libraries`，把 `page.has_more` /
`page.next_cursor` 丢掉了；`ResourcesPage` 的授权库区只渲染列表，没有继续读取入口；而且 `more()`
在 `!scope.library` 时直接 `return`——库列表这一级从来不是它的分支。库列表是**唯一**能打开库的
入口，所以第一页之后的库在这一版里没有任何路径可达。

**修的是分页本身，不是绕开分页**：

- hook 新增 `librariesPage`（`page` 元数据）与 `librariesConnection`（这份列表属于哪个连接）；
  `clear()` 一并清掉两者——切连接、撤权、会话过期都会让旧页消失。
- `more(cursor)` 现在有三个分支：搜索、目录、**授权库列表**。库列表分支把新页接在旧页后面，并且
  只在 `librariesConnection.current === found.connection` 时追加，否则整份替换：迟到的旧页写不进去
  （它同时受代号与 `AbortController` 约束）。没有做“全量自动读取”规避分页。
- 页面在 `page.librariesPage.has_more` 时给出显式按钮“继续读取下一页”，并写明“已显示 N 个授权库，
  上游还有更多”；读完则写“这一级已完整显示 N 个授权库”，不再留下按不动的按钮。
- 后端新增两条回归（**不需要新增任何端口**）：`test_authorized_library_list_pages_and_forwards_its_own_continuation`
  （137 个授权库、50/50/37 三页，游标是页面自己的不透明值、不是对端 token，遍历不重不漏）与
  `test_library_continuation_is_bound_to_the_listing_that_made_it`（目录列表的游标拿来当库列表游标
  是 409 `cursor_conflict`，不是“回答另一份列表”）。
- 浏览器侧新增两条闭环：多页库列表**真的读三页**（50 → 100 → 137，最后一页的库点进去能读到
  `第137库说明.txt`），以及切连接后上一份（含已读到的第二页）立即清空、不混在一张列表里。
- StrictMode 开发路径新增一条：续读只发**一次**带游标的请求、第一页只读一次、同一页不会被接两遍。

**顺带发现（合成装置的错，不是产品的错）**：第一版装置让对端只回 3 条却带上续读标记，平台按自己的
规则拒绝了它——「带续读标记的一页必须是完整一页」（`slice_page` 的 `cursor is None or len(items) ==
requested`）。这条规则是对的：短页会让“这一级已完整显示”变成谎话。装置改成按请求页大小返回、还有
剩余才带续读标记，于是三页真实闭环成立。

## 2026-09-17 接续返修：页面把自己的会话范围清掉

上一轮的提交只到后端（`5634150`），前端与浏览器套件没有收尾，因此协调未验收。接续时先复现了
一个确定的阻断，它不是测试写法问题：

**现象**：在真实浏览器里选定连接后，库列表能读出来（`assets/libraries` 返回 200、库行出现），
紧接着页面自己又发了一次状态读取，回答是 `connection: null`，库行消失，页面退回“请选择资产连接”；
再点库行时 `entries.browse` 得到 403 `connection_required`，目录永远打不开。

**根因**：前端的“我现在在哪”用的是 `POST /api/web/assets/connection`，请求体 `{}`。那个操作按设计
**丢弃**当前选择（它是“选择/放弃选择”的写入操作）。于是页面每读一次自己的状态就把范围清一次：
状态读取本身成了唯一的破坏者。用后端临时插桩确认过：同一个会话对象
（`id(session)` 不变）在 `ROUTE-IN` 里还带着 `assets: {connection_id: library-a}`，进到同一次
`connection` 调用后 `scope()` 已经是 `None`，而 `_read` 期间它一直在——被清掉的正是这一次调用。

**修的是语义分离，不是绕过去**：

- 后端新增只读操作 `POST /api/web/assets/state`（请求体必须是 `{}`）：只回答“有哪些允许的连接、
  当前选的是哪一个”，**永不改变范围**。`assets/connection` 仍然只负责改变，`{}` 仍然显式丢弃
  选择——这条语义没有放宽，只是不再兼任读取。
- 前端每次读取前的自检改走 `assets/state`；选定连接、切库、搜索、清除搜索、刷新、翻页的生命周期
  完全不变。
- 新增后端回归 `test_state_reads_never_change_the_chosen_connection`：连读三次状态后选择仍在、库
  列表仍读得出来、`state` 不接受 `connection_id`、显式丢弃仍然有效。浏览器侧新增
  `asset-library-dev.spec.ts`：StrictMode 首挂载复演之后库行仍在，且**一次清范围的 `connection {}`
  都没有发出**（按请求计数断言，不是靠肉眼）。

**回归真的能抓住这个阻断**：把 `useAssetPage.ts` 的状态读取改回 `assets/connection` 后重跑构建产物
套件，第一项用例在 `expect(library).toContainText("合成一号库")` 处超时失败，与手工复现一致；
改回 `assets/state` 后 4 项全过。

## 做了什么

“资料与资源 → 资产库”（`/#/resources/1`）从入口说明变成可用的真实只读页面：已授权连接与库、目录
分页、搜索、条目详情、来源与新鲜度、权限/离线/空/部分失败各自成状态。

- `services/platform/web_asset_queries.py`（纯规则）：五个上游操作的唯一白名单、每个标识/查询/
  路径/页大小/排序的边界校验、游标绑定（连接+库+范围+查询+排序）、对端回答与请求一致性校验
  （同库、同条目、命中属于它声称的库）、未知对端码归一成一个诚实的 `upstream_error`。无时钟、
  无网络、无存储、无全局状态。
- `services/platform/web_assets.py`（适配层）：同源端口 `assets/{state,connection,libraries,browse,
search,entry}`；会话里的范围（默认 900 秒）、`connection_required` 拒绝、读取台账（保留 32 条、
  展示 8 条，只记操作/码/取消，不记内容）、取消传播。
- `services/platform/web_console.py`：注册 `ASSETS_PREFIX` 分支，复用既有 Cookie/CSRF/Origin/Host
  与 **读后**会话与策略指纹复核。
- `apps/web/src/features/resources/`：`api.ts`（脱敏 DTO、错误映射、显示规则）、`useAssetPage.ts`
  （请求生命周期、代号取消、分页、会话变化清理）、`ResourcesPage.tsx`、`EntryList.tsx`、
  `DetailPanel.tsx`、`resources.css`。
- `apps/web/src/app/modules.ts` 一行 lazy 注册 + `App.tsx` 一行挂载（见下）。
- 隔离合成装置：`tests/backend/asset_fixtures.py`（真实 TLS 的合成 AssetLink 对端 + 场景开关）、
  `tests/backend/run_asset_web_fixture.py`（Playwright 用的三/四个 loopback 服务）、
  `apps/web/playwright.assets.config.ts`（构建产物）、`apps/web/playwright.assets-dev.config.ts` +
  `apps/web/vite.assets-dev.config.ts`（StrictMode 开发路径）。

   的只读浏览/搜索聚合”。它是让第 16 条（切库立即清旧正文）与第 15 条（无连接是一个独立状态）

   （`assets/connection {}`）会顺手把范围清掉。它不是第二个资产客户端，也不新增任何上游操作。
2. **`NoPreview` 的固定文案**。规格要求“只用类型图标与‘暂不提供预览’”；后端给的是原因句
   （“现行资产只读协议没有预览或下载端口，这里只显示索引元数据。”）。页面把两句都显示，不改
   后端已发布的 `preview.reason`。
3. **`App.tsx` 的一行挂载**。卡只授权 resources lazy 入口；`modules.ts` 的 lazy 注册不足以让页面
   出现（`resolveRoute` 已有 `resources` 段 1，但 `App.tsx` 的渲染分支里没有它）。改动是
   `else if (current.id === "resources" && section === 1) page = <pages.resources />;` 一行，与
   TS-017/TS-018 的挂载方式完全一致；没有重写全壳。
