# TS-372：同轮健康检查复用原生 backend 结果

基线为 `d214ec237858f4e5c9e949f3999ec499864a6023`，独立检出 `tianshu-platform-health/tianshu-platform`，分支 `codex/platform-health-backends-20261027`。本卡仅本地产品修复，产品 main、部署和生产数据均未操作。

## 问题与变更

原 `Probe.evaluate()` 的 store 与 sidecars 检查，以及 `preflight()` 的同两项检查，各自重复调用同一个 `backend_check`。原生 backend 自己已遍历全部已注册 schema；两次查询既重复工作，也可能使同一文档展示两个采样时刻的相反结果。

现由 store 完成该轮真实检查，将结果传给同轮 sidecars。独立 sidecar 检查仍可自行调用 backend；SQLite 各 sidecar 文件检查和独立 web account 检查继续原样执行。下一轮会重新调用 backend，失败结果也同样复用，不存在跨轮成功缓存。

保留原 9 项 readiness 检查、2 秒预算、1 秒缓存、按开始时刻判断缓存新鲜度、超时后的实际线程占有和晚到结果语义。没有修改依赖、数据库/权限、业务功能或 schema，也没有放宽真实错误。

## 验证

- 共享 Python 3.12.14、`tianshu-storage==0.1.3`，当前检出源码优先于已安装旧产品；冻结 text-dialogue 与 diagnostics 合同只读使用。
- `python -B -m unittest discover -s tests/backend -p test_runtime_health.py -v`：**94 passed，58.740 秒**，0 failure/error/skip。包含原本地 HTTP/TLS、预算/取消/缓存/晚到结果和 preflight 测试。
- 新增 4 项：每轮只查一次且下一轮重查；复用成功仍检查独立 account 故障；独立 sidecar 检查仍执行 backend；preflight 失败结果真实复用。
- 两个变动 Python 文件 Ruff check/format 及 `git diff --check` 通过。

实际 PG17 句柄计时由 TS-371/协调者另外测量，本卡测试使用既有 backend 回调端口覆盖调用次数和错误传播，未执行 NAS/PG 压力。已知实测 34 次句柄检查仍不足解释 2 秒超时，故本卡不宣称修复了候选的全部 HTTP 503 根因；后续实际 phase 计时由协调者继续定位，不能据此改长预算或把晚到成功洗成新鲜就绪。
