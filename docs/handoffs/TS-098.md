### 与卡片文字的差异（请审查确认）

1. `GroupTrace.list_kind` 额外记录该组来自 `whitelist` 还是 `blacklist`（首验已裁决保留）：没有这个**结构**字段，`rule_error` 时“哪个列表的哪一组出错”无法从决定本身读出。它是结构标记，不是判定输入。

3. 卡片第 4 节的 50 ms 是**单条 IPC 调用的上限**，实现按 `min(50 ms, 请求剩余)` 收紧，并在请求级用 5 s 收口；长期慢响应会先 `regex_timeout`、后 `evaluation_timeout`——两种码都有真实触发路径。

## 2. 冻结语义落地位置

- 逻辑：`accessible AND NOT quality_satisfied AND NOT blacklist_match AND (whitelist_empty OR whitelist_match)`；优先级 inaccessible → quality_satisfied → blacklist → whitelist → eligible；短路规则记 `not_evaluated`，绝不捏造 `not_matched`（`evaluator._judge`）。
- 组间 OR、组内 AND 且按输入顺序短路（`_run_groups`）；多值“任意一个值匹配”（`matching.any_value_matches`），不推断跨字段/跨作者关联。
- `title`/`description` 读 `original_*`（人工展示覆盖不改变判断）；`uploader_*` 只读 `role=uploader`；全空白来源视为缺失，任何操作都不匹配，包括 `regex=.*`。
- 全策略结构与正则语法先整体校验，非法规则不会潜伏在未命中位置：`evaluate` 抛 `RuleValidationError(invalid_regex, <list>[i].rules[j].value)`，与 `validate_policy` 一致；普通文本策略不启子进程。
- **启动期失败没有“已执行规则”**：worker 起不来时 `reason=regex_worker_failed`、`decision=rule_error`，每条规则记 `not_evaluated` + 该失败码，不伪造 `error` 规则。
- 摘要：`policy_digest(whitelist, blacklist, revision)` 对已校验参数按 UTF-8、`sort_keys=True`、`ensure_ascii=False`、紧凑分隔符、无尾换行求 SHA256。
- 错误只含固定词汇：不回显原值、表达式、文本、路径或凭据（`test_policy`、`test_purity`、`test_regex_process` 各有断言）。

### 真实子进程证据（同一份未改动的 worker 文件）

本机沙箱拒绝 `asyncio` 的 Windows 子进程传输（`asyncio/windows_utils.py` 的 `pipe()` → `PermissionError: [WinError 5]`），所以走事件循环的用例无法在此启动子进程。阻塞式 `Popen` 在同一沙箱可用，于是 `.runtime/probe_worker_protocol.py` 用**同一份 `regex_worker.py`、同一套行 JSON 协议**取证：

- 握手 `{"ready":true,"protocol":1,"pid":<真实 pid>}`，字段集合精确匹配，pid 与父进程看到的子进程一致；
- `-I` 下子进程默认编码实测为 `gbk`，而显式 UTF-8 重配后：`^动` 命中 `动画`、`🎬|合集` 命中 `🎬预告`、`STRASSE|straße` 在 IGNORECASE 下命中 `Straße`、`" 动画 "` 不匹配 `^动`（原文无损）；
- 非法表达式回 `{"seq":11,"ok":false,"code":"invalid_regex"}`，**响应中不含表达式文本**；`seq=true` 回 `{"seq":null,"ok":false,"code":"invalid_request"}`；未知操作回 `invalid_request`；
- 关闭 stdin 后子进程自行退出，退出码 **0**，`tasklist` 确认进程消失；
- `^(a+)+$` 对 40 个 `a` 的灾难回溯：`taskkill /F /T` 后 **0.05s** 内进程消失，父进程成功回收（退出码 1）；
- 退役逻辑（记录型传输，非子进程）：不肯退出的子进程被 kill 且记录真实 `returncode=-9`、回收在预算内（0.046–0.063 s）、第二次关闭不再等待也不再 kill、取消清理在 1.3 s 内完成并完成回收、自行退出的子进程无需 kill 且记 `0`；启动失败后不残留受管进程。

## 4. 风险与边界

- 沙箱内无法端到端证明“超时/取消后 `asyncio` 子进程真的消失”这条**传输层接线**：协议探针证明的是同一 worker + 同一 kill 方式，退役逻辑证明的是同一 `_retire` 路径但用记录型传输。协调环境复跑后此风险消除。
- **明确不承诺的部分（四轮 R1 的文字已按此更正，不再有“一秒内一定回收”的说法）**：句柄停在 worker 之外时（`create_subprocess_exec` 已产生子进程但尚未交回），worker **既不能 kill 它也不能 `wait` 它**。产品在这里承诺的是**有界且诚实的失败**——公共 `aclose()` 在 ≤1 s 内具名报 `regex_worker_failed`、`alive`/`settled`/`returncode` 如实、所有权不丢、迟到交接到达时由创建任务的失败收尾在创建自己的预算内 kill 并真实回收——而**不是**“关闭返回时那个子进程一定已经死了”。要覆盖后者需要让 `create_subprocess_exec` 可被安全中断（或把清理预算拉到长于创建耗时），两者都会改动冻结预算或依赖 asyncio 内部行为，本卡不做。**公共的有界返回、真实的回收、这一次关闭的结论是三个不同的状态**：`settled` 读传输层实时 `returncode`（孩子真退出后名额立刻回来、引用立刻解除），而“这一次关闭算不算成功”由那个清理任务自己的结果在结束时写一次、此后不再改写（五轮评审的三项发现正是把三者混在一起的结果）。
- 名额与清理的所有权语义是四轮的核心改动，五轮补上“结论与引用分开”，六轮补上“**实例的聚合结论由实例自己持有**”：`evaluator._active` 等于“请求 + 其未收尾资源”的份数，请求结束但孩子还活着时名额**照样占着**，第 3 个请求立即 `busy`；孩子真退出后名额与托管引用都归还**且只归还一次**，而这次关闭报过的失败**不会被改写成成功**（`test_bounds` 的真实子进程用例 + `.runtime/probe_round5_lifecycle.py`／`probe_round6_conclusion.py`／`probe_round7_cancel_close.py` 的记录式替身用例双向取证）。本机只能证明状态机顺序，真实“孩子还活着”只能由协调环境确认。
- 一个实例一生只有**一个由实例拥有的关闭**（`_closing`），聚合结论由那次关闭自己的结果记录、与“是否有调用方正常返回”无关：等待者被取消时取消**优先传播给该等待者**，共享关闭照旧等完（不新开期限、不取消收尾），结论也不会因为“集合现在空了”被重算成成功。代价是后续调用方**不再重新扫一遍集合**（旧行为允许“下一次关闭再扫”，也正是误报成功的来源）；真实退出的 worker 仍由实时 settlement 释放，失败只留一个有界布尔。这一处的真实子进程复验见 §3 的 `needs_validation`。
- 一个 worker 一生只有**一个**清理任务、deadline 只算一次：任何路径都不能替换它或把它往后推（四轮实测的 109 ms 推后即由此消除）。代价是“为另一个真正不同的孩子再开一轮清理”这种旧允许被**删掉**了——它正是推后 deadline 的来源；迟到孩子改由创建自己的失败收尾回收，因此不需要第二个清理。
- 本轮生命周期改动集中在“谁拥有创建任务、谁拥有清理任务、谁拥有实例的关闭结论”：`start`/`_call`/`aclose` 的失败路径共用同一个清理任务与 deadline，`aclose()` 的每个调用方加入同一个实例关闭，探针已逐条取证顺序（kill 先于 wait、关闭先关 stdin、创建期与交接期取消不留活子进程、并发关闭只花一份预算、取消的等待者不丢结论），但**真实**管道下交接窗口的耗时与取消组合只能由协调环境的实跑用例确认，本机不能自证。
- 夹具目录刻意不使用 `tempfile.mkdtemp`：在本沙箱里创建出来的 0700 目录之后连自己都无法列目录或删除（`os.listdir` / `os.rmdir` 都报 `PermissionError [WinError 5]`），因此夹具改用 `makedirs(mode=0o777) + chmod + 写入探针` 自证可用，测试才能实跑。上一轮遗留的 58 个空目录即由此产生，本轮实现不再产生新的残留。
- `input_too_large` 在**多值**字段上仍不可由合法数据触发（`tags` 上限 100×128 字符 = 37800 字节），该合计规则以 `projection_within_budget` 取证并在文档中如实标注。
- 卡片未要求、本卡也未实现：平台级并发限制（当前每实例 2，调用方只装配一个实例；不注册全局服务）、规则热更新、作业台账、来源扫描。
