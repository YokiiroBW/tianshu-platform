- 认领意图时校验 `expected_version` 仍是当前版本，因此旧版本并发发布仍然确定性地 409
  `version_conflict`（两个浏览器用例保持不变）；窗口一旦落库不可改写，过期窗口要求重新预览。
- 意图行只存摘要与窗口，不含端点、凭据引用或任何配置内容；权威库 schema 仍为 2，不动迁移主线。

### 修复的真实缺陷

网页发布文档的有效期窗口原先直接取 `time.time()` 原始读数：合同的时间戳编码会把微秒四舍五入，
而写事务随后用同一时钟再做一次 `published_at <= now` 检查；Windows 时钟粒度较粗时两次读数可能
落在同一个 tick 上，向上取整的时间戳就会比检查点晚约 0.5 微秒，发布被误判为 `invalid_input`。
表现为约一半概率的间歇失败（连续运行 20 次可复现）。修复方式是把窗口锚定到请求所在的整秒，
使时间戳在合同编码中精确往返、窗口长度恒等于 `lifetime_seconds`。修复后同一场景连续 20 次通过。

同时修正了网页侧一个错误提示被吞的问题：版本冲突后自动重读会先清空错误提示，操作者只看到
“已重新读取”而看不到冲突原因；现在重读后再回填错误，冲突原因与重读提示同时可见（浏览器用例断言）。

## 风险与限制

- 没有真实模型账号、供应商调用、付费模型、真实设备或生产部署；全部证据是合成 fixture 与本机
  loopback HTTP。根 `runtime_routes_enabled=false` 与 `runtime_disabled_until_joint_acceptance` 仍有效。
- 重放/意图账 `<db>.web-models.sqlite` 只存 client_id、语义摘要、目标、版本、文档摘要与窗口，
  不存端点或凭据引用；删除它只会让重放与恢复不再被识别，权威库里已提交的配置不受影响。它不随
  权威库自动清理，长期增长需要后续维护；备份/恢复必须与权威库一起保留，否则会出现
  `publication_unverified`。
- 网页管理是单机单管理员模型：没有双人复核、没有按版本的分页（最多列最近 20 版）、没有并发压测。
- `npm run format:check` 在仓库范围内仍有**先前就存在**的失败文件（`docs/handoffs/TS-013/015/064.md`
  与 `docs/platform/{assetlink,native-model-config,source-sync*}.md` 等未被本任务修改的文件）。
  本次只格式化了自己新增/修改的文件，未顺手改动无关文件。
- Playwright 官方 CDN 在本机不可达（`cdn.playwright.dev` ECONNRESET）；浏览器二进制改用
  Chrome for Testing 官方存储/镜像的同一版本（153.0.8010.12 = playwright chromium v1243），
  按 Playwright 期望的目录与 `INSTALLATION_COMPLETE` 标记放入 `%LOCALAPPDATA%\ms-playwright`
  （sha256 `415968b0…34c1` = chrome-win64.zip，`7aec872f…6c4c` = chrome-headless-shell-win64.zip）。
  未改动 `apps/web/playwright*.config.ts`，`node node_modules/@playwright/test/cli.js test
--config apps/web/playwright.web.config.ts` 命令本身不变。
- 网页套件需要 `TS012_CONTRACT_DIR` 指向已发布 `contracts/text-dialogue/v1`（`tests/backend/fixtures.py`
  在导入时读取该变量）；缺变量时合成后台无法启动而报 webServer 启动失败，属环境前置条件。
- 返修轮未覆盖的：真实断电/进程终止下的 SQLite 写丢失（用回执写失败、回执跳过与重启三类合成注入
  覆盖）；多操作者并发同一 `client_id` 的竞争（浏览器每次点击生成新 UUID，服务端以
  `INSERT` 唯一键认领，第二个并发请求会复用同一意图）。
