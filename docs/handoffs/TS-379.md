# TS-379 — 媒体后台不占满交互线程

基线 `06f093a96b76fe0dab74e18f9fa9566629738018`；独立分支 `codex/background-local-work-20261028`。仅本地产品实现，未连接 NAS/生产、未修改其他工作树。

实际触发：媒体 Music maintenance.plan 长持原 media 事务 advisory lock，另三线程等待同锁；原 LocalWork 四线程被后台占满，Gateway origin 续期虽已到 HTTP handler，仍等 executor 导致原3秒 bootstrap 超时。已知是池饥饿，无死锁证明。本卡不混入维护计划 N+1 SQL 优化。

## 变更

- `LocalWork(workers=4, capacity=16, *, background_capacity=None)` 原默认及 `run/run_settled/active/executor/drain/close` 接口保持；Platform 薄装配明确 `background_capacity=3`，**总线程4、原总准入16不变**。
- 可信媒体 `Background.run` 用 `background_scope()` 标记来源；作用域只携带 ContextVar，不持 worker permit。涵盖现有 books/comics/music/subscription/retention/worker 泵和其子任务；HTTP请求不根据输入或header选择优先级。其他独立后台不在本次自动分类范围。
- 一次 BG 同步操作先等独立3配额，再进原16准入。第4 BG等待不占 executor/shared槽位或其FIFO头部；未标记的交互可使用剩余线程。共享准入/唤醒规则抽为同文件私有 `_Capacity`，不另建任务库或队列系统。
- 两配额都跟随真实 concurrent future done；取消running调用不会提前还配额。取消准入前/共享队列/submit失败/queued future分别归还实际取得的配额，不重放操作。close唤醒两组等待者；drain同时等待两配额，仍保留callback准入到原cleanup关闭时。
- 既有 copy_context 继续传播来源。实际 music scan/worker/publication 路径在每次 `media.local(...)` 返回后才进行远端async await，未跨远端等待持permit；桥传播意味着后台发起的回调仍属BG，不通过伪装身份变成前台。局部测试的新callback task证明ContextVar继承与remote等待期零permit，**不冒称它就是完整跨模块桥联验**。
- `Probe.ready` 本来使用独立默认executor、单在途与原2秒预算；本卡不改其检查、缓存或期限。原Store、权限、认证、协议、媒体事务/串行锁、取消回执及业务语义不变。预留线程解决已证明的后台池饥饿，不承诺任意前台重负载/数据库锁都零等待。
