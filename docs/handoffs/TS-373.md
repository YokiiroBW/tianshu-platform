# TS-373：凭据健康检查复用已拥有的存储 runtime

从 TS-372 的 `e58732f6807fb49afd33d26c2da352216090a404` 继续，独立分支 `codex/platform-health-credentials-20261027`，检出仍为 `tianshu-platform-health/tianshu-platform`。产品 main、远端和生产数据均未操作。

## 已证实的问题与修复

协调者的 TS-371 installed-clone 计时将主要重复开销定位到 `_credentials`：每个凭据名都调用 `credential_present()`，其 `WebAccount(settings)` 未带已拥有的 runtime，继而重新执行 `backends.readonly(settings)` / `StorageRuntime.inspect()`。这包括普通服务凭据，而不只是 setup token。

`credential_present(settings, name, *, runtime=None)` 现在透传 WebAccount 原有的 runtime 能力；Platform 的 `HealthInputs` 回调传入其 `self.storage_runtime`，不再重新检查后端绑定。仍逐项构造 WebAccount、读取实际所需账户状态并解析当前 secret，不缓存账户结论或敏感值。已提交账户允许移除一次性安装 token 的原规则、独立 account 健康检查及凭据缺失失败均保持。

没有已拥有 runtime 的 CLI `_preflight()` 仍走原默认只读路径。仅将 `sqlite3.Error` 和原 `Fault` 一同映射为凭据不存在，覆盖复用的 StorageRuntime 已关闭后真实抛出的 `StorageError`（其为 `sqlite3.OperationalError` 子类）；没有吞通用异常或把关闭状态报健康。

没有更改九项健康检查、预算、缓存/晚到语义、关闭时序、namespace、marker、数据库内容、权限、账户合同或依赖。
