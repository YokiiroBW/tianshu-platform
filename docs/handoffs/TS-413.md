# TS-413 受信操作员后台记忆恢复入口

基线 `aff6345`；分支 `codex/ts413-recovery-management-20261029`。本卡仅本地开发，协调者负责推送与 R23 发布，不修改前端或根入口。

## 原因与变更

TS-408 Companion recovery 已部署，但统一外部 TLS/internal 路由只到 Platform。不能通过无监听的 Companion hostname 直接调用。新增 Platform 固定 POST `/internal/v1/memory/learning/recover`，沿既有 operator Bearer 身份、平台内部 Companion client factory 和 `management_call` 转发。

正文仍为原六字段：actor_id、job_id、request_id、expected_attempts、expected_failure_count、model_request_id。上传限制 4096 字节、严格 JSON/字段/ID/整数验证；只有 `role.manage` 且 kind=operator 的当前身份可用，角色须属于该 operator、active、enabled 且有 memory.write。没有创建浏览器伪 session、权限、凭据、数据库或第二队列。

转发使用原 `settings.core` 的 platform→Companion 凭据和 `client_factories['companion']`；仅允许固定端点。一次 HTTP 命令只转发一次，不自动重试、不换 request_id。已转发后的未知网络结果复用原 mutation/error 边界，返回 execution_state=unknown、retryable=false、保留原 request_id。操作员只可重发原六字段，最终幂等与原 job/batch/源核验仍属于 Companion。响应 resumed 不是 Memory 已完成写入。

Host 原排空/入口隔离机制保持；没有单独监听、绕过 TLS 或改根代理规则。普通网页与 Cookie 不开放此入口。

## 验证

新增四个原生 HTTP 用例，采用合成 Platform 独立 SQLite 状态与合成 Companion HTTP owner；覆盖 401/403、角色权限拒绝、原命令/原配置凭据单次转发、响应丢失的 unknown 与同键重发、严格正文和 4096 字节边界。Linux 使用协调者已安装依赖的固定 R21 镜像、只读 candidate mount、network none、临时 /tmp，无生产卷、安装、模型调用。

协调者已对精确源码提交 `39d7ea6e7ef4c775bb3825b36985fa19794eefd0` 执行 Linux 原生 HTTP 四节点：**4 passed，2.345 秒**。固定镜像 `sha256:1850b49ac5a489f4d8d2994446fcc1176c158319a8ccc1557220e6874bef97fe`；零生产 mount、零依赖安装、零模型调用。根证据 `ts413-linux-targeted-result.json`；包与四节点清单在本 worktree `.runtime/ts413/validation-package.json`，archive SHA-256 `0a6f364bce2f8802b5455bda2494928dbfc7be72ad43b486b12ca7a63eb46c64`。

本地新模块/测试 Ruff 检查、server/transport 必要语法规则及 diff 空白检查通过。此次结果回填只改文档，复用已通过结果，不重跑全量、浏览器、双后端或生产验证。协调者另发现的 Platform 角色 pending/verify 原因归 TS-414；本入口保持 active 检查，不为恢复绕过角色状态。

## 操作约束

协调者先确认 Gateway 容量已修正及原 model_request_id 的 admission 排队取消证据，再使用已登记 operator 的原 Bearer 经统一 TLS 入口发送原六字段。错误若为 unknown，不据此清状态或更换请求键。角色关闭、记忆写权限移除、原 CAS 改变时正常拒绝；不能借 operator 身份绕开 Companion 的原任务和源检查。
