## 0.1 第三轮返修（F2 遗留的第二次取消）

协调方复验 `fd40da3e`：F1/F3/F4/F5 与单次取消均已闭合，只剩一项——**连续两次取消时确认期限消失**。
`confirm_async` 在等待前把序号记入 `_owed`，但该集合只由「真实写完 / 失败 / 退出」结算，没有独立期限；
第二次取消会取消 `wait_for` 本身，于是「到期即报未确认」的那段代码永远不会执行，等待者也没注销。
慢盘一直不返回时，接管责任只是一条内存记录：400ms 后仍 `durable`/`unconfirmed=0`。

修复（`services/platform/diagnostics.py`，不新增路径、不新增 task/Timer/线程）：

- `confirm_async` 捕获 `asyncio.CancelledError`：**就在等待被取消的当刻**结算这份责任——注销等待者、
  把该序号计入 `unconfirmed`、`_fail("log_flush_timeout")` 让 sink 转 `unavailable` 并阻止新业务，
  然后**原样重抛**取消异常。这正是返修卡允许的第一种方式（等待被取消时立即保守标记未确认并阻止新业务），
  它不依赖 IO owner 从永远阻塞的 write 返回，也不需要第二个期限或后台任务。
- 上界仍然只有一个（单调的 `terminal_timeout`）；正常单次取消的语义完全不变：仍在同一上界内结算，
  到期才转不可用并计数。
- `admit_durable_async` 同样注销被取消的等待者（防止终止的等待积累），但**不**把 sink 判为故障：
  准入被取消时没有任何人得到过确认承诺，记录照常排队等待 owner 写入。
- 已受理记录不丢弃、不重发、业务结果不变；取消异常永远照原样传播。

协调方场景的独立复现（同一条流程：真实 TLS 上游挂起、hold 日志 write、第一次取消进入终态确认、
30ms 后第二次取消、不释放磁盘、400ms 后观察，最后 release+flush 仅作收尾）：

| 观察点（400ms，磁盘仍被 hold） | 修复前 `cancel-result.json` | 本候选实测                            |
| ------------------------------ | --------------------------- | ------------------------------------- |
| `state_after_400ms`            | `durable`（假成功）         | `unavailable`                         |
| `unconfirmed`                  | `0`                         | `1`                                   |
| `_owed` / 注册等待者           | 未断言                      | `[]` / `0`                            |
| `sequence` / `synced`          | `2` / `1`                   | `2` / `1`（记录仍在队列，未丢未重发） |

回归：`CancellationSettlementTests` 重写二次取消用例为「不释放磁盘且超过原 250ms 期限」并断言
未确认/不可用/等待者清理/记录仍在队列，新增「被取消的准入只注销等待者、不虚构故障」用例；
单次取消、持久成功、write/sync 失败与 close 交错用例保持不变并继续全绿。

## 3. 关键实现决定（供审查）

1. **先 fsync 再确认**：`emit_durable` 只在 fsync 返回后推进 `_synced`；「已确认」不等于「可能在
   内存里」。
2. **一个写线程独占文件**：开段、写入、fsync、封存、关闭都由同一线程完成，调用方只等待结果。
   慢盘让调用方等到自己的上界，不阻塞事件循环，也不让别人替它写。
3. **等待分「被唤醒」与「已确认」**：写失败唤醒等待者时它们**失败返回**，不把失败当成成功；
   `recover()` 只有在真实写入成功后返回真值。
4. **关闭有界且不抢文件**：`close` 立刻拒绝新业务，超预算返回「未确认」，写线程仍自行封存关闭，
   超时计入 `unconfirmed` 并反映到就绪检查。
5. **关停结论是结算，不是系统调用结果**（F1）：`close`/`flush` 只有在「全部已受理事件已 fsync
   **且**分段已封存」时才为真；空文件封存成功不能把未写队列说成成功，seal 失败永远不为真，失败
   不被后续重复 `close`/`flush` 覆盖。及时退出与持久成功是两件事，前者由 owner 是否结束表达，
   后者由 `_final_ok` 与 `unconfirmed` 表达。
6. **未确认事件保留可核对状态**（F1）：写失败/超预算时事件留在队列里（恢复仍可写入），
   `unconfirmed` 按**不同序号**计数、只增不减，既不靠丢队列也不靠无限等待来「变绿」。
7. **终态责任先交给 sink，再等待**（F2/0.1）：取消/正常/异常出站终态与入站取消先 `hand_over` 再在
   终态上界内确认。上界只有一个（单调的 `terminal_timeout`）；**等待本身被第二次取消时就在当刻保守
   结算**（计入 `unconfirmed`、sink 转 `unavailable` 并阻止新业务、注销已终止的等待者），因此
   「没人再等」永远不等于「已确认」；被取消的准入只注销等待者、不虚构故障。没有无界后台 task/线程，
   业务结果不变、不重发。
8. **缓存按检查开始时刻计龄**（F3）：过预算/过 TTL 的迟到结果落地即为陈旧，下一次请求真的重新
   检查；owner 只由工作本身释放，取消不堆叠。
9. **一条规则一处实现**（F4）：发布生命周期由 `Models` 的纯函数校验，启动与预检调用同一函数，
   不复制、不放宽；预检仍不建库不迁移。
10. **鉴权结论要有证据**（F5）：只有「密码校验通过」或「出示本部署签发的有效会话」才算认证成功，
    由控制台显式标记；Cookie/Authorization 头的存在、进入 console、鉴权前拒绝、未知路径都不冒充
    成功（保持 `not_attempted`）；Host/Origin/CSRF 未削弱。
11. **容量耗尽拒绝新业务**：目录到上限时 `ready=false` 且新业务 503，不静默丢记录、不假装健康。
12. **日志失败不重发副作用**：出站调用失败或取消只记录，不因日志问题重试已发出的动作；取消时用
    `outbound_not_sent` 区分「没发出」与「可能已发出」。
13. **未知不等于健康**：`not_verified` 与 `non_durable` 都阻塞就绪；探针并发调用不重复起核对，
    取消也不堆叠。
14. **`not_configured` 是部署选择，不是故障**：只核对本部署**实际拥有**的 sidecar 台账。
15. **探针不写日志**：探针请求（含未通过认证的）不产生任何记录；业务请求全量登记、不采样。
16. **就绪凭据独立且每次读取**：复用业务凭据值、空值、空白值都在请求时返回 503；两变量同值在
    启动时以 `invalid_input` 拒绝。
17. **入口与预检同源**：`preflight` 调用 `validate_settings`，与 `serve` 判同一件事；纯校验不建库、
    不迁移、不写文件。
18. **合同按原始字节固定**：manifest 覆盖 CRLF 文件，任何行尾规范化都会失败；`Contracts` 自身的
    LF 规范化不适用于诊断包。
19. **只读就是只读**：数据库只用 `mode=ro`（从不用 `immutable`），`PRAGMA query_only=ON`。
20. **容器自己构建控制台**：`console` 阶段按锁文件 `npm ci` + `npm run build`，运行阶段无 Node；
    `.dockerignore` 排除本机 `dist`，镜像内容不可能是作者机器的遗留产物。

## 4. 风险

| 风险                                                          | 影响与缓解                                                                                                                                                                                          |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **容器镜像从未构建、从未运行**                                | 最高风险项。`Dockerfile` 只经过静态核对；层缓存、非 root 写权限、`HEALTHCHECK` 实际行为均未验证                                                                                                     |
| 镜像内 `npm ci` + `npm run build` 未执行                      | 本机无 Docker，构建阶段只在静态核对层面被证明；需在具备 Docker 的环境执行第 5 节第 1 项                                                                                                             |
| Windows 上 `loop.add_signal_handler` 抛 `NotImplementedError` | 已回退到 `signal.signal`；POSIX `SIGTERM` 路径**未在 Linux 上验证**                                                                                                                                 |
| 诊断合同状态为 `development_frozen_pending_joint_acceptance`  | 联合验收前合同仍可能变更；manifest 哈希已按协调方更正固定，若合同再变必须重新核对                                                                                                                   |
| 日志目录无保留期/轮转删除                                     | 到上限即拒绝新业务（刻意的），运维侧需要自行归档或扩容，否则长时间运行会触发 503                                                                                                                    |
| `preflight` 在首次启动前报 `requires_initialization`          | 这是正确语义而非故障；编排脚本必须区分「未初始化」与「坏了」                                                                                                                                        |
| sidecar 台账纳入就绪检查                                      | 台账与权威库必须一起备份；删掉台账会让 `sidecars` 转红                                                                                                                                              |
| 真实对端（核心网页、人格、HA、静态上游）可用性                | 不在本卡范围；`credentials: ok` 只表示变量在环境里，不表示对端可达                                                                                                                                  |
| `HEALTHCHECK` 依赖证书 SAN 覆盖 `127.0.0.1`                   | 未覆盖时健康检查会正确地失败（`healthcheck` 用 `ssl.create_default_context(cafile=…)` 且**保持主机名校验**，所以证书必须带 `127.0.0.1` 的 IP SAN）；这是部署前置条件而非产品缺陷，见部署文档第 4 节 |
| 关停结论可能比真实结算更保守                                  | 超预算的 `close` 返回假，即便 owner 随后真的把事件写完：这是刻意的（「未能确认」不等于「已持久」）。真正失败的 `_final_ok` 永不为真，可核对状态保留在 `unconfirmed` 与队列里                        |
| 终态确认上界默认 250ms（`terminal_timeout`）                  | 慢于该上界的磁盘会让调用方超时并转入 `unavailable`（拒绝新业务，需显式恢复）；这是「宁可拒绝也不假成功」的选择，运维需为日志目录准备正常延迟的存储                                                  |
